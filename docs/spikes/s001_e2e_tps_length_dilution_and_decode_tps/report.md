# Spike report

## 问题

在 200K 超长上下文基准评测中，实测发现 Antigravity（E2E TPS 181~213，输出 12K~17K tokens）表面上大幅领先 OpenCode（E2E TPS 114，输出 3.8K tokens）。需要验证：该性能差距究竟是来自服务商底层物理吞吐差异，还是因为模型输出 token 数量不同，导致固定的超长预填开销（TTFT 约 12~15 秒）被摊薄程度不同所引发的阿姆达尔效应偏差？

## 成功判据

在相同模型与渠道（`cpa/gemini-3.8-flash` via OpenCode）下，通过提示词控制变量，要求模型详尽展开生成 10,000+ tokens：

1. 若端到端 TPS 发生跃升并抹平与 Antigravity 的差距（达到 180~200 tok/s）；
2. 且扣除预填后的生成时间窗 TPS 保持高度一致（250~270 tok/s）；
    则证实端到端 TPS 与输出 token 数量强正相关，反映模型真实纯输出能力的是生成 TPS。

## 尝试

在保持 200K Django 源码切片（27.1 万输入 tokens）完全一致的前提下，进行长短两组对比调用：

- 对照组（短输出）：默认提示词，模型收敛总结；
- 实验组（长输出）：提示词要求逐类逐函数深度剖析，输出 10,000+ tokens。

## 证据

|评测组|账单输入 Token|输出 Token 数|端到端耗时 (Wall)|解码生成时间窗|**端到端 TPS (E2E)**|**纯生成 TPS**|
|---|---|---|---|---|---|---|
|**OpenCode 对照组 (短)**|268,878|3,869|33.6s|14.2s|**114.77 tok/s**|**272.83 tok/s**|
|**OpenCode 实验组 (长)**|271,739|**10,575**|53.8s|41.4s|**196.54 tok/s** 🔥|**255.74 tok/s**|
|**Antigravity (多文件实测)**|207,920 ~ 305,817|12,241 ~ 17,117|80.3s ~ 81.3s|约 50s ~ 60s|**150.5 ~ 213.2 tok/s**|约 200 ~ 240 tok/s|

**数学解析**：
端到端 TPS = `输出 Token ÷ (TTFT 预填时间 + 解码时间)`。

- 在 200K 场景下，预填时间（12~15s）是固定的沉没成本；
- 当输出仅 3,800 token 时，预填时间占总耗时近一半，分母严重被固定预填时间摊薄，导致端到端 TPS 显得很低（114）；
- 当输出达到 10,575 token 时，预填耗时在总时长占比被大幅稀释，端到端 TPS 直接飙升至 196.54，抹平与 Antigravity 的差距；
- 扣除预填后的纯生成 TPS 始终极其稳定在 **255 ~ 273 tok/s**，证明两者的底层物理引擎完全同速。

## 结论

1. **强相关性确立**：在 200K 超长上下文场景下，端到端 TPS 与输出 Token 数量存在极强的正相关性（输出越长，预填被摊薄得越薄，E2E TPS 计算值显得越高）。存在“作文越长跑分越占便宜”的统计偏差。
2. **纯生成 TPS 是核心基准**：扣除预填耗时的流式生成吞吐（生成时间窗 TPS）不随输出长度剧烈波动，真实反映了大模型底层解码硬件单元的物理生成速度。

## 是否采纳

- 决定：是。
- 理由：彻底澄清了长上下文测速指标的物理本质，指导后续基准指标的呈现与命名。
- 后续 task：沉淀技术发现 `d001`，并更新规范文档与指标说明。
